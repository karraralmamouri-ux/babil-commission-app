## الحالة الفعلية

- المستودع يحتوي على `index.html` فقط في خط الأساس.
- الملف يجمع HTML وCSS وJavaScript وبيانات ابتدائية في نحو 780 سطراً و62,841 بايت.
- GitHub Pages يعرض الصفحة بنجاح.
- المصادقة تتصل بـSupabase عبر عميل REST خفيف داخل الملف.
- ملف المستخدم يقرأ من `profiles`.
- إدارة المستخدمين تستدعي Edge Function باسم `admin-users`؛ استُرجع مصدرها ومصدر `admin-create-user` من لوحة Supabase إلى المستودع.
- بيانات العمولات والأرشيف وسجل التدقيق تحفظ في `localStorage` تحت مفاتيح منها `babil_commission_v2`.
- يوجد baseline معاد البناء ومهاجرة أمنية forward-only ومصادر Edge Functions؛ أُعيد بناء Staging منهما، وأضيف CI لتشغيل الاختبارات على Pull Requests و`main`.
- فرع `main` محمي بفحص CI إلزامي strict يطبق على المسؤول، مع linear history ومنع force-push والحذف واشتراط حل المحادثات؛ لا توجد tags بعد.
- طُبقت مهاجرة لمساري تحديث العمولة وتسجيل الصرف عبر RPC ذري مع idempotency وoptimistic concurrency وaudit منظم على Staging والإنتاج؛ رُبطت الواجهة بمسار الصرف، بينما ربط تعديل العمولة ما زال مؤجلاً.
- أضيفت أداة قراءة فقط لفحص نسخة `localStorage`، والتحقق من SHA-256، واستخراج أعداد ومجاميع المطابقة دون طباعة أسماء الوكلاء.
- نجحت 56 مطالبة Auth/RLS/RPC فعلية على Staging للأدوار الأربعة، وتحقق حذف fixture وسجلاته وسحب منح الكتابة المالية المباشرة.
- أُصلح سجل migrations في الإنتاج بتسجيل الإصدارات الثلاثة المطبقة سابقاً دون إعادة تنفيذها، ثم طُبقت مهاجرة RPC وحدها وأصبح السجل up-to-date.
- تطابقت أعداد وبصمات جداول الإنتاج الستة قبل وبعد المهاجرة: profileان، فترتان، 82 صف عمولة، وثلاثة جداول فارغة.
- صُدرت نسخة المتصفح التشغيلية بصيغة الإصدار 1، وتحققت بصمتها وبنيتها دون طباعة أسماء الوكلاء.
- أضيفت مطابقة محلية/مركزية للقراءة فقط. أثبتت أن الفترة المحلية لا تطابق أياً من الفترتين المركزيتين، وأن الفترتين المركزيتين متطابقتان في المحتوى؛ لم تُكتب أو تُحذف أي بيانات نتيجة ذلك.
- أضيف وضع بيانات مركزية اختياري خلف زر صريح. يستخدم جلسة المستخدم وRLS، يتحقق من كامل الصفوف والشرائح قبل العرض، ويسمح فقط بصرف المدير والمحاسب عبر RPC ذري مع رجوع فوري للحالة المحلية.
- تحفظ جلسة Supabase في المتصفح وتجدد تلقائياً قبل انتهاء access token أو بعد أول 401، مع الاحتفاظ بها عند انقطاع شبكة مؤقت ومسحها عند رفض refresh token.

## ما يعمل وفق قراءة الكود

- تسجيل الدخول والخروج عند توفر Supabase والحسابات الصحيحة.
- قراءة دور المستخدم وتقييد عناصر الواجهة.
- حساب الكميات والاستحقاق والمتبقي وحالة الصرف.
- البحث والتصفية ولوحات الملخص.
- إضافة الوكلاء وتعديلهم وحذفهم محلياً حسب الدور.
- الأرشيف الشهري المحلي والتصدير إلى CSV.
- استيراد CSV الأساسي.

## ما هو معطل أو غير موثوق

- كان ملف مكتبة Excel المنشور يرجع HTTP 404؛ عولج بنسخة SheetJS مثبتة واختبار round-trip، وتحقق نجاحه في GitHub Pages بعد دمج PR #3.
- بيانات الصرف المركزية مشتركة بين الأجهزة والمتصفحات؛ بقية تعديلات العمولة ما زالت محلية.
- صرف RPC يكتب سجل تدقيق مركزياً؛ سجل التعديلات المحلية القديم يبقى محلياً وقابلاً للمسح.
- الحفظ المؤجل يعرض التعديلات للفقد قبل «حفظ الشهر».
- صلاحيات البيانات المالية ليست محمية خادمياً لأن البيانات محلية.
- مقارنة الوكيل تعتمد على الاسم، وترتيب بعض الأشهر نصي.
- الشهر الجديد يعتمد على تاريخ الجهاز لا الشهر المفتوح.
- لا يملك الإنتاج سجلاً تاريخياً في `supabase_migrations`، لكن baseline المعاد البناء وسجل Staging المثبت يجعلان مخطط التطبيق قابلاً لإعادة الإنشاء على بيئة فارغة.
- الخطة المجانية لا توفر scheduled database backups.
- كانت سياسة `profiles_update` تسمح للمستخدم بتحديث صفه مع `UPDATE` على كل الأعمدة؛ أُغلق المسار في الإنتاج بالمهاجرة `20260804183000_harden_authorization.sql` وتحقق منع التعديل بمحاكاة دوري admin وaccountant.
- جدولَا audit المركزيان فارغان، ويوجد نموذجان متداخلان للعمولات والتدقيق.

## الخطوة التالية

1. ينفذ المحاسب أول دفعة إنتاجية معتمدة من وضع البيانات المركزية، ثم يتحقق مستخدم ثانٍ بزر «تحديث» من ظهورها وسجلها؛ لا تستخدم دفعة وهمية للاختبار.
2. تسجيل أي جهاز أو متصفح تشغيل إضافي وتصدير نسخته دون دمج أو استبدال، ثم اعتماد مصدر الأشهر المختلفة؛ يبقى الاستيراد التلقائي ممنوعاً.
3. بعد اعتماد مصدر كل فترة، يبدأ ربط `update_commission_row` تدريجياً، وتبقى الإضافة والحذف والإلغاء مؤجلة إلى RPCs وقواعد تجارية مستقلة.

# دليل التشغيل

## فحص سريع للحالة الحالية

1. تحقق من أن GitHub Pages يعرض `index.html`.
2. تحقق من تسجيل الدخول بحساب اختبار.
3. لا تدخل بيانات إنتاجية لأغراض الاختبار.
4. صدّر CSV قبل أي عملية قد تستبدل البيانات المحلية.

## النشر الحالي

- المصدر: فرع `main`.
- المستضيف: GitHub Pages.
- لا يوجد build مخصص في خط الأساس.
- بعد أي نشر، افحص HTTP 200، شاشة الدخول، RTL، Console، ومسارات الموارد.

## تشغيل Staging

- مرجع Staging هو `unohqhxubraelqgjhxgh`، ويجب ألا يساوي مرجع الإنتاج `qolrsefpbvfuugwyqggu`.
- معلومات الربط والحسابات تحت `work/runtime/` فقط، وهي مستبعدة من Git.
- قبل أي migration: `db push --dry-run` ثم نسخة محلية وتحقق من الهدف.
- بعد التطبيق: `npm test` ثم `npm run test:staging` بالمتغيرات الموضحة في `docs/STAGING.md`.
- `db reset --linked` مسموح على Staging بعد التحقق من المرجع وعدم وجود بيانات مطلوبة؛ ممنوع على الإنتاج.
- انشر `admin-users` إلى Staging واختبر قبول المدير ورفض غير المدير. لا تنشر الوظيفة القديمة `admin-create-user` دون قرار أمني منفصل.
- اختُبر dump بصيغة custom والاسترجاع على Staging. عند `pg_restore` استبعد `DEFAULT ACL` الخاصة بـ`supabase_admin` من قائمة الاسترجاع فقط، مع إبقاء بقية ACL؛ راجع البصمة والإجراء في `docs/STAGING.md`.

## النسخ الاحتياطي الانتقالي لـlocalStorage

يستطيع المدير إنشاء ملف من زر «نسخة احتياطية JSON». الملف يحفظ الفترة المفتوحة، الوكلاء، الشرائح، الأرشيف وسجل التعديلات، مع إصدار للصيغة وبصمة SHA-256. لا ينسخ جلسة Supabase أو رموز الدخول.

1. نفّذ التصدير من كل جهاز ومتصفح يُستخدم فعلياً؛ البيانات المحلية قد تختلف بينهما.
2. لا تعدل الملف ولا تغير اسمه قبل تسجيل الجهاز والمتصفح وصاحب النسخة ووقت التصدير في جرد الترحيل.
3. خزّن الملف في مساحة مشفرة ومقيدة الوصول، ولا ترفعه إلى Git أو ترسله في قناة عامة.
4. لا تستورد الملف في التطبيق الحالي؛ لا توجد آلية استرجاع معتمدة بعد.
5. عند الترحيل، تحقق آلياً من `format` و`version` وبصمة `integrity` قبل تحليل البيانات، ثم اعرض الفروقات والتعارضات للمراجعة البشرية.

لفحص نسخة دون تعديلها أو استيرادها:

```powershell
npm run inspect:backup -- "C:\المسار\babil_commission_backup_....json"
```

يجب أن تكون `valid` و`checksum.matches` بقيمة `true`. يحسب التقرير الأعداد والكميات والمستحق والمدفوع والمتبقي، ولا يطبع أسماء الوكلاء. أي خطأ أو اختلاف بصمة يوقف الترحيل ولا يُصحح الملف يدوياً.

لمطابقة النسخة مع تصدير مركزي محفوظ محلياً دون كتابة أو كشف أسماء:

```powershell
npm run reconcile:backup -- "C:\المسار\backup.json" "C:\المسار\central-export"
```

راجع `docs/RECONCILIATION.md`. اختلاف الشهر أو المحتوى يبقي `safeToAutoImport=false` ويوقف الدمج التلقائي، لكنه لا يمنع الاستمرار في بناء أدوات القراءة والمعاينة الآمنة.

## المعاينة المركزية

زر «معاينة البيانات المركزية» يقرأ الأشهر والصفوف المسموح بها عبر جلسة المستخدم وRLS. تظهر لافتة زرقاء واضحة، وتتعطل عمليات التعديل والصرف والحذف وإدارة المستخدمين والنسخ الاحتياطي حتى الرجوع إلى النسخة المحلية.

1. لا تستخدم المعاينة كاعتماد لمصدر الشهر؛ راجع تقرير المطابقة أولاً.
2. تحقق من ظهور لافتة «للقراءة فقط» ومن اختفاء/تعطيل كل مسارات الكتابة.
3. بدّل بين الأشهر من القائمة فقط، ثم ارجع إلى النسخة المحلية وتأكد من عودة الشهر والمجاميع والتعديلات غير المحفوظة كما كانت.
4. فشل الشبكة أو التحقق يبقي النسخة المحلية دون تغيير.
5. لا تختبر المعاينة بحساب أو بيانات إنتاجية جديدة؛ القراءة تستخدم البيانات الموجودة فقط.

## مهاجرات الحفظ المالي

- المهاجرة `20260804230000_add_atomic_financial_rpcs.sql` مطبقة ومتحقق منها على Staging والإنتاج؛ لا تعِد تطبيق baseline على إنتاج قائم.
- شغّل `npm test` أولاً، ثم `db push --dry-run` على مرجع Staging، ثم اختبارات الأدوار الحقيقية.
- بعد تطبيقها، الكتابة المباشرة لجداول العمولات والتدقيق مرفوضة؛ استخدم RPC المراجع فقط.
- لا تربط الواجهة بالإنتاج قبل اختبار replay لنفس `request_id`، رفض التعارض القديم، رفض الدفع فوق المستحق، ووجود audit واحد لكل عملية ناجحة.

البصمة تكشف التعديل أو التلف العرضي، لكنها ليست توقيعاً رقمياً ولا تثبت هوية منشئ الملف.

## الاسترجاع المستهدف

1. تحديد آخر نسخة سليمة ووقت الحادث.
2. إيقاف الكتابة إن كان استمرارها يزيد الضرر.
3. استرجاع إلى بيئة منفصلة أولاً.
4. مقارنة أعداد الوكلاء والكميات والمستحق والمدفوع والمتبقي لكل شهر.
5. اعتماد مسؤول العمل قبل تبديل الإنتاج.
6. توثيق الحادث والسبب والإجراء الوقائي.

## فشل النشر

- لا تعدل `main` بسرعة دون معرفة السبب.
- راجع commit وGitHub Pages job والموارد المفقودة.
- ارجع إلى آخر commit معروف عبر revert قابل للتدقيق، لا بإعادة كتابة التاريخ.
- تحقق أن قاعدة البيانات لم تتغير مع نشر الواجهة قبل الرجوع.

## فشل Supabase أو الشبكة

- اعرض الواجهة بوضع آمن ولا توهم المستخدم بأن الكتابة نجحت.
- لا تكرر دفعة دون idempotency key.
- احتفظ بالإدخال المؤقت غير الحساس فقط وفق تصميم معتمد.
- راجع logs وrequest ID قبل إعادة العملية.

## معلومات الوصول المطلوبة لاحقاً

- مالك GitHub وإعدادات Pages وbranch protection.
- مسؤول Supabase وبيئة Staging.
- حسابات اختبار للأدوار الأربعة.
- مسؤول اعتماد المجاميع المالية والترحيل.

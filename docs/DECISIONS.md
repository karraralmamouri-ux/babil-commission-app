# سجل القرارات

تسجل القرارات دون حذف القديم. الحالات: Proposed, Accepted, Superseded, Rejected.

## ADR-001 — المحافظة قبل إعادة الهيكلة

- التاريخ: 2026-08-04
- الحالة: Accepted
- القرار: يمنع تنفيذ إعادة كتابة ضخمة. يُنشأ خط أساس واختبارات، ثم تقسيم تدريجي مع بوابة قبول لكل مرحلة.
- السبب: التطبيق مالي والبيانات الحالية موزعة محلياً، ولا توجد اختبارات أو migrations.

## ADR-002 — Supabase مصدر الحقيقة المستهدف

- التاريخ: 2026-08-04
- الحالة: Accepted
- القرار: تصبح قاعدة Supabase المصدر المركزي بعد ترحيل ومطابقة آمنين؛ يقتصر `localStorage` لاحقاً على تفضيلات غير حساسة.
- السبب: دعم تعدد المستخدمين والتدقيق والاسترجاع.

## ADR-003 — GitHub Pages للواجهة فقط

- التاريخ: 2026-08-04
- الحالة: Accepted
- القرار: يستمر GitHub Pages في استضافة الواجهة، وتبقى الأسرار والعمليات الإدارية في Supabase.

## ADR-004 — وحدات TypeScript قبل اختيار framework UI

- التاريخ: 2026-08-04
- الحالة: Proposed
- القرار المقترح: استخدام Vite وTypeScript وES Modules دون إدخال React فوراً. يعاد تقييم framework عند ثبوت حاجة تعقيد الواجهة.
- السبب: تقليل نطاق التغيير مع الحصول على build وأنواع واختبارات.

## ADR-005 — الدفعات كسجل معاملات

- التاريخ: 2026-08-04
- الحالة: Proposed، يحتاج قراراً تجارياً
- القرار المقترح: كل دفعة سجل مستقل، والإلغاء موثق دون حذف.

## ADR-006 — نسخة انتقالية إصدارية دون استرجاع مباشر

- التاريخ: 2026-08-04
- الحالة: Accepted
- القرار: يصدّر المدير فقط مستند JSON بالإصدار 1 يحتوي مفاتيح الحالة التشغيلية المحددة وبصمة SHA-256 على `state`. تُستبعد جلسة المصادقة، ولا يضاف الاستيراد قبل بناء تحقق ومعاينة وتعارضات.
- السبب: نحتاج جرد نسخ الأجهزة قبل Supabase مع منع الاستبدال غير المقصود أو تحويل ملف نسخ غير موثوق إلى كتابة مباشرة.
- القيد: SHA-256 فحص سلامة وليس توقيع هوية أو تشفيراً؛ حماية الملف مسؤولية التخزين والنقل.

## ADR-007 — إدارة profiles خادمياً فقط

- التاريخ: 2026-08-04
- الحالة: Accepted
- القرار: يمنح المستخدم المصادق `SELECT` على profile المسموح فقط، ولا يمنح `INSERT` أو `UPDATE` أو `DELETE` مباشرة. إنشاء الحسابات وتغيير الدور والحالة وكلمة المرور يمر عبر `admin-users` بعد التحقق من JWT وprofile إداري نشط.
- السبب: سياسة تعديل الصف الذاتي تسمح بتغيير عمود `role` وتكسر كل فحوص الإدارة التي تعتمد على profile.

## ADR-008 — لا تغيير schema دون نسخة محلية في الخطة المجانية

- التاريخ: 2026-08-04
- الحالة: Accepted مؤقتاً
- القرار: قبل أي SQL يغير schema أو policies تُصدر جداول التشغيل محلياً مع SHA-256 وتُراجع الأعداد. يستبدل هذا الإجراء المؤقت بـfull dump ونسخ مجدولة/PITR عند تجهيز البيئة المناسبة.
- السبب: مشروع Supabase الحالي على Free Plan ولا يملك scheduled backups.

## ADR-009 — baseline معاد البناء وStaging منفصل

- التاريخ: 2026-08-04
- الحالة: Accepted
- القرار: يُحفظ مخطط التطبيق الحالي في baseline مخصص للبيئات الفارغة، مع حارس يرفض التطبيق إذا وجدت جداول التطبيق. يُختبر baseline مع migrations اللاحقة على مشروع Staging مستقل قبل أي تغيير إنتاجي.
- السبب: الإنتاج سبق سجل migrations ولا يمكن دفع baseline إليه بأمان، بينما نحتاج بيئة قابلة لإعادة الإنشاء واختبارات Auth/RLS حقيقية.
- التحقق: أُعيد بناء Staging من الصفر، وطابق كتالوج الإنتاج، ونجح اختبار الأدوار الأربعة وEdge Function الإدارية.

## ADR-010 — الكتابة المالية عبر RPC ذري فقط

- التاريخ: 2026-08-04
- الحالة: Accepted ومطبق في قاعدة الإنتاج؛ رُبط مسار الصرف بالواجهة وما زال ربط تعديل العمولة مؤجلاً
- القرار: تمنع جلسات المتصفح من الكتابة المباشرة إلى جداول العمولات والتدقيق. تمر تعديلات بيانات العمولة وعمليات الصرف عبر دوال `SECURITY DEFINER` تتحقق من الدور والمدخلات، تقفل الصف، تكشف التعارض بواسطة `updated_at`، تمنع تكرار `request_id`، وتكتب `audit_logs` في المعاملة نفسها.
- السبب: إخفاء الأزرار وRLS الجدولي وحدهما لا يضمنان ذرية السجل المالي أو منع إعادة إرسال الدفعة.
- الحدود: إنشاء الأشهر، الحذف، الإلغاء، وقفل الفترة تبقى خارج هذا القرار إلى أن تحسم قواعدها التجارية وتضاف RPCs مستقلة.
- التحقق: طُبقت المهاجرة على Staging، ونجحت 56 مطالبة للأدوار الأربعة شملت replay والتعارض ومنع تجاوز المستحق وذرية audit، ثم تحقق تنظيف fixture.
- تحقق الإنتاج: طابقت الجداول الستة نسختها السابقة بالبصمة والعدد، وأصبح سجل migrations محدثاً؛ لم تكتب المهاجرة بيانات مالية.

## ADR-011 — المطابقة قراءة فقط ولا تعتمد مصدراً تلقائياً

- التاريخ: 2026-08-05
- الحالة: Accepted
- القرار: تُقارن نسخة المتصفح مع تصدير الجداول المركزية محلياً دون شبكة أو كتابة. لا يطبع التقرير أسماء الوكلاء، وتبقى `safeToAutoImport=false` حتى عند تطابق المحتوى.
- السبب: اختلاف مفتاح الشهر أو المحتوى قد يمثل نسخة تشغيلية مستقلة أو خطأً يحتاج اعتماداً؛ تحويل نتيجة المطابقة مباشرة إلى استيراد قد يكرر أو يستبدل بيانات مالية صحيحة.
- التحقق: اختبارات المطابقة تغطي التطابق الكامل، المحتوى نفسه تحت شهر مختلف، تغير الحقول، وتكرار المحتوى المركزي، مع إثبات عدم ظهور هويات الصفوف في التقرير.

## ADR-012 — المعاينة المركزية اختيارية وللقراءة فقط

- التاريخ: 2026-08-05
- الحالة: Superseded جزئياً بـADR-013؛ يبقى الرجوع المحلي وتعطيل التعديلات غير المالية نافذين
- القرار: تُحمّل `commission_months` و`commission_rows` عبر جلسة المستخدم وRLS عند طلب المستخدم فقط. تحفظ الواجهة الحالة المحلية في الذاكرة، وتعطل كل صلاحيات الكتابة والصرف والحذف وإدارة المستخدمين والنسخ الاحتياطي، وتوفر رجوعاً فورياً إلى الحالة المحلية.
- السبب: نحتاج إثبات القراءة المشتركة وسلامة التحويل قبل تحويل Supabase إلى مصدر الواجهة أو تفعيل RPCs في الإنتاج.
- الحدود: المعاينة لا تحفظ اختيارها، ولا تكتب إلى قاعدة البيانات أو `localStorage`، ولا تعرض سجل التدقيق المركزي بعد.
- التحقق: يغطي الاختبار تحويل المخطط، رفض القيم المالية غير الآمنة، وجود مسار الرجوع، وعدم وجود طلبات كتابة إلى جدولي العمولات.

## ADR-013 — الصرف المركزي والجلسة المستمرة

- التاريخ: 2026-08-05
- الحالة: Accepted
- القرار: يتحول وضع البيانات المركزية من معاينة صامتة إلى قراءة مشتركة تسمح حصراً بعملية الصرف للمدير والمحاسب عبر `record_commission_payment`. تبقى تعديلات الكميات والأسعار والحذف معطلة. تحفظ جلسة Auth في تخزين المتصفح، ويجدد العميل الخفيف access token قبل انتهائه أو بعد أول 401 مع تسلسل refresh واحد وتحديث refresh token المدور.
- السبب: الصرف المحلي المؤجل كان قابلاً للفقد ولا يظهر لبقية المستخدمين، ورمز access القصير كان يوقف الجلسة المحفوظة بعد انتهائه. RPC المنشور يوفر التحقق الخادمي والذرية وسجل التدقيق ومنع تكرار الطلب وكشف التعارض.
- سلوك الفشل: لا تتغير الواجهة قبل نجاح RPC؛ يعاد استخدام request id عند فشل شبكة مبهم، ويعاد تحميل السجل عند تعارض `updated_at`. لا تمسح جلسة الدخول بسبب انقطاع شبكة مؤقت، لكنها تمسح عند رفض refresh token.
- الحدود: إنشاء الأشهر وتعديل العمولات والإلغاء والتصحيح تبقى غير متاحة مركزياً حتى اعتماد قواعدها وإضافة RPCs مستقلة.
- التحقق: اختبارات الواجهة تثبت جسم RPC وقيم concurrency/idempotency، وتحويل سجل التدقيق المركزي، وبقاء الجلسة عبر إعادة التحميل، وتدوير refresh token، وعدم مسح الجلسة عند فشل شبكة مؤقت.

## قرارات معلقة

- الفصل بين `monitor` و`viewer`.
- صلاحية المحاسب في الإلغاء والتصحيح.
- دورة اعتماد وقفل الشهر.
- وحدة المبلغ وقبول الكسور.
- سياسة معرف الوكيل ونقل المنطقة.
- مدة الاحتفاظ والنسخ الاحتياطية.

## ADR-014 — الواجهة الأصلية مع استيراد خام مهيأ خارج الكود

- التاريخ: 2026-08-09
- الحالة: Accepted
- القرار: تبقى الواجهة الداكنة الأصلية ووظائف التير اليدوي والأسعار كما هي. يتغير مسار الاستيراد فقط ليحسب من الملف الخام باستخدام `id` الفريد و`parent` والباقات الثلاث المعتمدة.
- الإعدادات: تحفظ خريطة الوكلاء والفروع ونطاقات الكابينات في `assets/data/raw-import-config.json`، ويمكن للمدير تعديل نسخة محلية منها من الواجهة دون تعديل كود الحساب.
- الزون القديم: تجمع كميات حسابات `parent` التابعة للوكيل لتحديد التير التلقائي فقط، ثم يسجل كل حساب رئيسي أو فرعي في صف مستقل ويطبق عليه سعر تير المجموعة. يبقى التير اليدوي متاحاً على مستوى الصف للحالات الاستثنائية.
- الزون الجديد: تحدد الكابينة من `lastname`، وتنسب لصاحب النطاق بغض النظر عن parent، ويحدد التير لكل كابينة منفردة.
- السلامة: إعادة الرفع تحفظ التير اليدوي والمدفوع وتاريخ الصرف عند تطابق اسم السجل، وتعرض ملخصاً للأصناف المتجاهلة والحالات غير المعرفة.

## ADR-015 — البيانات المركزية هي مساحة العمل الافتراضية

- التاريخ: 2026-08-09
- الحالة: Accepted
- القرار: بعد تسجيل الدخول تحمل الواجهة البيانات المركزية تلقائياً وتعرضها كمصدر التشغيل اليومي، مع سايدبار للتنقل ومؤشر حالة وآخر تحديث. لا تعرض الواجهة للمستخدم تسمية «النسخة المحلية».
- تجهيز الشهر: يحتفظ التطبيق بالحالة المحفوظة في المتصفح داخلياً لمسار إداري صريح باسم «وضع تجهيز الشهر». تظهر فيه فقط للمدير أدوات رفع الملف الخام وتغيير التير والأسعار والحفظ وإنشاء الشهر.
- سلوك الفشل: عند تعذر القراءة المركزية تخفى بيانات التشغيل السابقة ويظهر تنبيه وإجراء إعادة المحاولة، حتى لا تُفهم بيانات قديمة على أنها بيانات مركزية حديثة.
- الحدود: اعتماد نتائج الشهر مركزياً يحتاج مسار كتابة واعتماد خادمياً منفصلاً؛ لا توحي الواجهة بأن الحفظ الإداري المحلي قد نُشر مركزياً.

## ADR-016 — اعتماد الشهر المركزي وتحرير الأرشيف

- التاريخ: 2026-08-09
- الحالة: Accepted للتطبيق، Pending deployment لقاعدة البيانات
- القرار: يستطيع الأدمن اختيار أي شهر مركزي يدوياً وفتحه كنسخة تجهيز قابلة للتعديل، ثم نشره فقط عبر `publish_commission_month`. لا تكتب الواجهة مباشرة إلى جداول الأشهر أو الصفوف.
- التير والربط: يحفظ كل صف التير المطبق، وضعه التلقائي/اليدوي، كمية مجموعة التير، معرف المجموعة، حساب `parent` والمالك. يتحقق الخادم من التير والمستحق قبل الكتابة ويحافظ على الصرف المسجل.
- الإعدادات: تحفظ خريطة الاستيراد المشتركة عبر `save_import_settings` للأدمن، مع قراءة مركزية ونسخة متصفح احتياطية مؤقتة قبل نشر المهاجرة.
- صلاحيات الأدمن: تبقى إدارة المستخدمين والنسخ الاحتياطي متاحة في العرض المركزي؛ تعديل العمولات يتم في وضع التجهيز ثم الاعتماد، والصرف يبقى مركزياً ومدققاً.
- الأرشيف والتقارير: يعرض التطبيق مقارنة شهرية واتجاه صعود/نزول الوكلاء، ويصدر تقرير Excel بصيغ حساب وإعدادات قابلة للمراجعة. أزيلت بيانات العمولات التجريبية من المصدر.
- إدارة الأرشيف: يستطيع الأدمن عرض أو فتح أو تصدير أو استيراد الفترة المختارة. ملف الفترة مستقل، يحمل الشهر وبصمة SHA-256، ويرفض إذا لم يطابق الشهر المختار أو احتوى قيماً مالية غير آمنة. الاستيراد يذهب إلى وضع التجهيز ويحافظ على الصرف المركزي المعروف ولا ينشر تلقائياً.
- النشر: يجب اختبار المهاجرة على Staging قبل الإنتاج، ولا يعد حفظ مسودة التجهيز نشراً مركزياً.
- الإطلاق الأول: تبدأ الواجهة المركزية دون فترات ظاهرة. تضيف المهاجرة `is_visible=false` للفترات الموجودة قبل الإطلاق وتحفظها دون حذف، ثم تجعل الفترات الجديدة ظاهرة افتراضياً؛ يعيد اعتماد فترة قديمة إظهارها صراحةً.

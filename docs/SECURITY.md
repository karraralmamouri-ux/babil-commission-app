# الأمان

## نموذج الثقة

المتصفح غير موثوق. إخفاء زر أو فحص الدور في JavaScript يحسن التجربة لكنه لا يمنح حماية للبيانات. الحماية المطلوبة في Postgres RLS وRPC/Edge Functions.

## المفاتيح

- Publishable/Anon key مسموح في الواجهة عند وجود RLS صحيح.
- `service_role` وأسرار الإدارة ممنوعة في Git والمتصفح وGitHub Pages.
- الأسرار الخادمية تحفظ في Supabase secrets أو مخزن أسرار مناسب.
- `.env` محلي ومهمل من Git؛ `.env.example` أسماء فقط.

## الصلاحيات المستهدفة

- `admin`: إدارة النظام ضمن سياسات خادمية مدققة.
- `accountant`: قراءة البيانات المالية وإنشاء عمليات الصرف المسموحة فقط.
- `monitor` و`viewer`: قراءة وفق قرار الفصل بينهما.
- إدارة Auth تمر عبر `admin-users` بعد التحقق من JWT والدور الحالي خادمياً.
- المستخدم لا يعدل دوره أو `is_active` بنفسه.

## سجل التدقيق

- append-only للمستخدمين العاديين.
- يسجل الممثل، الإجراء، الكيان، قبل/بعد، الوقت وrequest ID.
- الحذف أو التنظيف التشغيلي سياسة إدارية منفصلة مع احتفاظ ونسخ احتياطية.

## نتيجة تدقيق Supabase في 2026-08-04

- جميع جداول `public` تستخدم RLS. كانت سياسة `profiles_update` الأصلية مع منح `UPDATE` تسمح نظرياً بتغيير المستخدم لدوره بنفسه؛ طُبقت مهاجرة مستقلة وأُغلق المسار في الإنتاج.
- لا توجد نسخ قاعدة بيانات مجدولة على الخطة المجانية؛ أُخذ تصدير محلي ببصمة قبل أي تغيير.
- `admin-users` يتحقق خادمياً من المستخدم والدور والحالة النشطة، وأصبح مصدره محفوظاً في Git.
- جدولَا التدقيق فارغان، وكانت هناك سياسة حذف إدارية على أحدهما؛ أزالت المهاجرة الأمنية الحذف المباشر وجعلته append-only للمستخدمين.
- تحقق ما بعد النشر من غياب grants لـ`anon`، واقتصار profiles للمستخدم المصادق على `SELECT`، وغياب سياسات mutation؛ كما نجحت محاكاة سياسات admin وaccountant داخل transaction مع rollback.
- التقرير التفصيلي: `docs/SUPABASE_AUDIT_2026-08-04.md`.

## مخاطر الحالة الحالية

- البيانات المالية وaudit في `localStorage` قابلة للتعديل.
- inline handlers و`innerHTML` يوسّعان سطح XSS ويحتاجان تقليلاً واختبارات ترميز.
- الجلسة يديرها عميل مخصص ولا يظهر refresh متكامل.
- البيانات المركزية لا تزال غير مستخدمة من الواجهة المالية؛ اكتمل اختبار سياسات admin وaccountant، وما زال اختبار تسجيل الدخول الفعلي للأدوار الأربعة في Staging مطلوباً.
- GitHub Pages لا يضيف CSP خاصة بالتطبيق؛ يمكن دراسة CSP عبر meta بعد حصر المصادر.

## استجابة الحوادث

عند الاشتباه بتسريب أو تعديل غير صحيح:

1. لا تحذف السجلات أو الأدلة.
2. قيّد الحساب المتأثر من Supabase.
3. احفظ logs ووقت الحادث ونسخة البيانات.
4. دوّن النطاق والإجراءات في سجل حادث منفصل غير عام إذا احتوى بيانات حساسة.
5. استرجع من نسخة مختبرة ثم تحقق بالمجاميع المالية.
